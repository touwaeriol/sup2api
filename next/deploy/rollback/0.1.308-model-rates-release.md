# 核心 0.1.308：倍率四层取一，折扣和按倍数规则换算成倍率（迁移 0124，单向）

核心 0.1.308 带迁移 0124（CONTRACTS §97.10）。迁移是单向的，会删数据（用户分组的折扣、账号分组按倍数的规则），**不能滚动升级**。所有环境都升级完、不再回退后删除本文件。

## 这次升级改变了什么

- 新表 `group_model_rates`（账号分组 × 模型的倍率）、`segment_model_rates`（用户分组 × 账号分组 × 模型的倍率）。倍率只取一个，四层里最具体的一层生效，不再相乘（CONTRACTS §97.1）。
- 折扣不等于 1 的用户分组（含个人专属），在每个还没有用户分组倍率的账号分组得到 `基本倍率 × 折扣`（4 位小数四舍五入，封顶 999999.9999），然后删掉 `segments.discount`。
- 每条按倍数的规则（账号分组 g、模型 m、倍数 N）变成 g 对 m 的模型倍率 `N × 基本倍率`，以及 g 里每个有用户分组倍率 R 的用户分组对 m 的用户分组模型倍率 `N × R`（同样舍入、封顶），然后删掉这些规则和 `price_rules.multiplier`；`price_rules` 只剩独立价格，`kind` 恒为 `custom`。
- 升级瞬间每个用户在每个账号分组、每个模型上付的钱不变，只差舍入和极端的封顶。之后改基本倍率，换算出来的倍率不再跟着变；折扣换算出的用户分组倍率比账号分组的模型倍率具体，升级后新设的模型倍率对这些用户分组的成员不生效（CONTRACTS §97.10“等价性”）。
- 接口：删除 PUT `/groups/:id/model-prices`、PUT `/segments/:id/groups`、PUT `/groups/:id/segments`，改为随 POST/PATCH `/groups`、`/segments` 一次写入；`/segments` 去掉 `discount` 并严格解析请求体；模型价格去掉 `kind`；各倍率列表项的 `rate` 必填（CONTRACTS §97.6）。
- 迁移之后旧核心（0.1.307）的鉴权读不到 `segments.discount`、价格快照读不到 `price_rules.multiplier`，无法服务请求，新旧核心不能混跑。

## 一、发布前：只读检查，结果交给所有者

以下都只读，对升级前的线上库执行（只读副本也可以），结果原样交给所有者（用户）看，所有者确认换算符合预期后再继续。

1. CONTRACTS §97.10“发布前对线上库只读检查”的全部查询（第 1–5 条）：折扣不等于 1 的用户分组（带 `is_default`，默认用户分组有折扣时等于给全平台换算）、会写入的 `segment_groups` 行数、按倍数的规则、规则所在账号分组里已有的用户分组倍率、升级后应得的 `group_model_rates` / `segment_model_rates` 行数、会舍入或封顶的倍率。查询以 CONTRACTS 里的文本为准，不在这里抄第二份。记下第 1b、3、4 条的数字，第四节核对要用。
2. 第 5 条有结果时，要让所有者知道这些调用升级后的单价会有最多 0.00005 倍的差别（或被封顶），由他决定是否升级前先调整基本倍率、折扣或规则。
3. 用新核心的二进制运行价格检查（CONTRACTS §131.8），全部通过（退出码 0）再继续：

   ```sh
   sub2api admin check-prices
   ```

## 二、确认有升级前的数据库备份

发布者不自己备份数据库。升级前向所有者确认：已有一份升级前的数据库备份，或数据库服务的时间点恢复能覆盖到停机这一刻。没有得到确认不升级。

## 三、停机升级

- 发布包按 [gateway/README.md](../gateway/README.md) 打，含迁移，带 `SOURCE_SCHEMA`（0.1.307 核心的 `schema-contract` 输出）。
- 预检必须是 `primary-first-v1`（从节点先转发到主节点并停止，主节点最后停机、迁移、启动，再逐个恢复从节点），不能走 `rolling-v1`。单节点环境同样是一次停机升级。
- 网关不变，内置插件随核心升级，不需要单独处理。
- 控制台随核心一起发布：升级后刷新页面。旧页面保存账号分组价格或用户分组会调到已删除的 PUT 接口（404），或因请求里的 `discount` 收到 400。直接调这些接口的脚本要按新形状改（CONTRACTS §97.6）。

## 四、升级后核验

- `schema_migrations` 里有 `0124_model_rates.sql`。
- 行数与第一节记下的一致：

  ```sql
  SELECT
    (SELECT count(*) FROM group_model_rates)   AS group_model_rates,    -- = 第 4 条 expect_group_model_rates
    (SELECT count(*) FROM segment_model_rates) AS segment_model_rates,  -- = 第 4 条 expect_segment_model_rates
    (SELECT count(*) FROM segment_groups WHERE rate_override IS NOT NULL) AS segment_rates,  -- = 升级前已有的用户分组倍率 + 第 1b 条
    (SELECT count(*) FROM price_rules WHERE kind <> 'custom') AS non_custom_rules,           -- = 0
    (SELECT count(*) FROM information_schema.columns
      WHERE table_schema = current_schema()
        AND (table_name, column_name) IN (('segments', 'discount'), ('price_rules', 'multiplier'))) AS dropped_columns;  -- = 0
  ```

- 挑一个有折扣的用户分组成员、一个按倍数规则的模型，在控制台“试算”（POST `/pricing/quote`）里看倍率与来源：分别是 `segment`（基本倍率 × 折扣）和 `group_model`（N × 基本倍率），与升级前实付一致。
- 经网关各发一个非流式、流式请求，使用记录 `billed`，`rate_multiplier` 与试算一致；节点日志没有 ERROR。
- 用户侧“我的模型”选一个账号分组，每行的倍率与试算一致（`GET /me/prices?group_id=` 的 `rate`）。

## 五、之后：删掉 `scale` 兼容代码

0124 之前冻结了按倍数规则的待结算记录仍按冻结的 `scale` 结算（CONTRACTS §97.4）。升级完成一段时间后，在每个环境跑 §97.4 里的只读查询（`frozen_scales`）；所有环境都是 0 之后，下一个版本删掉 `core.PriceRule.Scale`、`core.PricingTrace.Scale` 和 `usage` 的 `frozenRule.scale`。

## 六、出问题时

- 迁移改了 schema，网关不允许跨 schema 回退核心（升级计划和 `sub2api-gateway rollback` 都会拒绝）。优先修复前进。
- 必须回退时，只能用旧版核心（0.1.307）和第二节确认过的升级前备份一起恢复。恢复之后，备份时刻以后的使用记录、余额流水和配置改动都随之丢失，要先告诉所有者。
- 某个用户分组或模型的倍率不对，不用回退：在账号分组的“价格”“用户分组倍率”页或用户分组的“账号分组倍率”页改掉，保存后下一个请求生效（模型倍率在价格快照里，提交后广播失效，CONTRACTS §97.6“何时生效”）。
