# 核心 0.1.307：计费方式只留可视化与表达式、模型价格只属于分组（迁移 0122、0123，单向）

核心 0.1.307 带迁移 0122（按 token 的阶梯条件，CONTRACTS §131）和 0123（删除用户组专属价，CONTRACTS §97.10）。两个迁移都是单向的，0123 还会删数据，**不能滚动升级**。所有环境都升级完、不再回退后删除本文件。

## 这次升级改变了什么

- 0122：`per_token` 改名 `visual`，档位的 `max_len` 换成 `when` 条件；`per_request` 改成单个按次档（保留原规则）；`price_rules.mode` 只允许 `visual`、`expression`。表达式和哈希不变。
- 0123：删除 `price_rules` 里 `segment_id` 非空的行（用户组与个人专属的模型价格），删掉 `segment_id` 列，规则按（分组, 模型）唯一。删掉的专属价不会自动回来。
- 自定义价不再有“失效”判定：0.1.306 上因全局价改了形状而失效的分组自定义价，升级后会**开始生效**，取代全局价计费（CONTRACTS §131.4）。
- 迁移之后旧二进制读不了 `price_rules`，无法计费，新旧核心不能混跑。

## 一、发布前：只读检查，结果交给所有者

以下都只读，对升级前的线上库执行（只读副本也可以）。三项的结果原样交给所有者（用户）看；有结果的项要等所有者决定后再继续。

1. 用新核心的二进制运行价格检查（CONTRACTS §131.8）：

   ```sh
   sub2api admin check-prices
   ```

   全部通过时退出码 0。有输出（编译不过的表达式、生成不出所存表达式的配置）就先改那些价格，再跑一次，直到通过。

2. 升级后会开始生效的自定义价（CONTRACTS §131.4 的查询，0.1.306 的口径）：

   ```sql
   SELECT r.group_id, r.segment_id, r.model, r.mode AS custom_mode, m.mode AS global_mode
   FROM price_rules r JOIN model_prices m ON m.model = r.model AND m.enabled
   WHERE r.kind = 'custom' AND r.mode IS DISTINCT FROM CASE
     WHEN m.mode = 'per_request' AND jsonb_array_length(COALESCE(m.config->'rules', '[]')) = 0 THEN 'per_request'
     WHEN m.mode = 'per_token' AND jsonb_array_length(m.config->'tiers') = 1
       AND COALESCE(m.config->'tiers'->0->>'unit', '') IN ('', 'token')
       AND jsonb_array_length(COALESCE(m.config->'rules', '[]')) = 0 THEN 'per_token'
   END;
   ```

   有结果时由所有者决定每条删掉还是保留；要删的在升级前从控制台删掉。`segment_id` 非空的行会被 0123 删掉，不用单独处理。

3. 0123 将删除的专属价（CONTRACTS §97.10 的查询）：

   ```sql
   SELECT r.group_id, r.segment_id, r.model, r.kind, r.multiplier, r.mode
   FROM price_rules r
   WHERE r.segment_id IS NOT NULL
   ORDER BY r.group_id, r.segment_id, r.model;
   ```

   有结果时所有者要知道这些价格会消失；需要保留的价格只能改设到分组上（分组内定价），升级前做或升级后照结果重建。

## 二、确认有升级前的数据库备份

发布者不自己备份数据库。升级前向所有者确认：已有一份升级前的数据库备份，或数据库服务的时间点恢复能覆盖到停机这一刻。没有得到确认不升级。

## 三、停机升级

- 发布包按 [gateway/README.md](../gateway/README.md) 打，含迁移，带 `SOURCE_SCHEMA`（0.1.306 核心的 `schema-contract` 输出）。
- 预检必须是 `primary-first-v1`（从节点先转发到主节点并停止，主节点最后停机、迁移、启动，再逐个恢复从节点），不能走 `rolling-v1`。单节点环境同样是一次停机升级。
- 内置插件随核心升级，不需要单独处理。
- 控制台随核心一起发布：升级后刷新页面；旧页面保存分组价格会因请求里的 `segment_id` 收到 400。

## 四、升级后核验

- `schema_migrations` 里有 `0122_tier_conditions.sql` 和 `0123_drop_segment_price_rules.sql`。
- 再跑一次 `sub2api admin check-prices`，全部通过（升级后它还检查每条可视化价格的配置能否生成所存表达式）。
- `SELECT mode, count(*) FROM model_prices GROUP BY mode;` 只有 `visual`、`expression`；数量与升级前 `per_token` + `per_request` 的和一致。
- 第一节第 2 项里所有者决定保留的自定义价，在分组的价格页显示为自定义价，试算按它计价。
- 经网关各发一个非流式、流式请求，使用记录 `billed`，费用与价格一致；节点日志没有 ERROR。

## 五、出问题时

- 迁移改了 schema，网关不允许跨 schema 回退核心（升级计划和 `sub2api-gateway rollback` 都会拒绝）。优先修复前进。
- 必须回退时，只能用旧版网关、旧版核心（0.1.306）和第二节确认过的升级前备份一起恢复。恢复之后，备份时刻以后的使用记录、余额流水和配置改动都随之丢失，要先告诉所有者。
- 价格上的问题（某个自定义价开始生效后金额不对）不用回退：在分组的价格页改掉或删掉那条自定义价，保存后立即生效。
